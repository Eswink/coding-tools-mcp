# Official API basis (read-only research)

These Microsoft pages were retrieved over ordinary public HTTPS (200). They are API documentation, not execution evidence. A first guessed fileapi/GetFileInformationByHandleEx URL returned 404; the corrected winbase URL returned 200. Fetch manifests retain both observations.

- [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile): a relative ObjectName resolves under the actual RootDirectory handle. FILE_CREATE requires a new file and fails on an existing name. Check actual NTSTATUS plus IoStatus.Information, not only a nonzero raw handle. FILE_OPEN_REPARSE_POINT does not itself prove a regular object.
- [OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes): OBJ_DONT_REPARSE stops reparse traversal with STATUS_REPARSE_POINT_ENCOUNTERED. New controls must construct genuine reparse objects and observe the real API result; ordinary path rejection is a different branch.
- [FILE_ID_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info): bind the volume serial and complete 128-bit file ID; a path or partial ID is not object identity.
- [FILE_STANDARD_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info): inspect actual link count, directory/type and delete state alongside the existing object checks.
- [GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex): handle-based information queries are native observations; a JSON fixture is not this query.
- [DuplicateHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-duplicatehandle): DUPLICATE_SAME_ACCESS with inheritance disabled is useful, but duplication alone does not independently establish a stronger sharing restriction.
- [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew): sharing DELETE governs later opens for delete access. The proposed directory pin test must first establish delete access with all other directory handles sharing DELETE, reject it while the new pin exists, then accept it after checked close. This avoids treating a child-file sharing failure as proof of the directory pin.
- [CloseHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-closehandle): nonzero confirms success; zero with GetLastError is a failed operation. A controlled protected-handle fault is not production closure, and a stale numeric raw value is not a live handle. The existing uncertain owner remains retained without retry or removal.

No Rust input module visibility, production Go code, owner authorization, gate or publication behavior is changed. Ordinary owned test fixtures grant no VM, publisher or release permission.

- [SetHandleInformation](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-sethandleinformation) and [GetHandleInformation](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-gethandleinformation), actualHTTP200: HANDLE_FLAG_PROTECT_FROM_CLOSE prevents CloseHandle from closing that live handle. The new isolated fault sets/reads this real flag, calls the original closeKnown once, observes the uncertain retained owner and actual still-live pinned identity, and never clears/retries it. This avoids racing an invalidated numeric value with OS handle reuse. It is deliberate native fault injection, not a production unknown-close incident.
