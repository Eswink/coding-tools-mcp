# Design

## 概述

Use only the required finite two-channel OVERLAPPED parent pipe adapter with unchanged original native process/Job definitions. The current source has no new adapter implementation. Avoid a synchronous PeekNamedPipe loop: Microsoft only guarantees immediate return in a single-threaded application and warns synchronous handles in a multithreaded application may block. No unchecked thread assumption supplies retirement proof.

## 技术方案

FR-1 preparation: CreateNamedPipeW uses FILE_FLAG_FIRST_PIPE_INSTANCE|FILE_FLAG_OVERLAPPED, local-only byte-mode pipe, non-inheritable server and a fresh finite random name. Create a non-inheritable manual-reset event and stable OVERLAPPED before ConnectNamedPipe; retain all actual returns immediately. Open the actual write client in this manager, complete the specific connection (including a documented already-connected return), then validate the retained pair. The stdin endpoint is an actual read handle for the local NUL device, not an input ownership claim. Set and read back inheritance on exactly the child stdin/stdout/stderr endpoints, and construct the real PROC_THREAD_ATTRIBUTE_HANDLE_LIST over those retained actual values. Retain attribute storage and original environment/command buffers through CreateProcessW. Immediately retain actual process/thread; assign the actual no-breakaway Job while suspended; close each parent copy of child endpoints only after checked CloseHandle success; ResumeThread only after all required preparation/closure succeeds. Any pre-resume uncertainty denies; suspended real child/Job retirement remains an independent attempt. Named pipe client PID may be a diagnostic corroboration only; actual owned returns and exact API binding are the boundary.

FR-2 read state: each channel owns one event/OVERLAPPED/buffer and at most one issued read. A real ReadFile failure other than IO_PENDING before an operation is issued is classified separately; only explicitly documented EOF/error outcomes can close a channel normally, all unfamiliar outcomes fail/retain as appropriate. A true immediate completion is consumed once with its actual byte count; a pending read is observed by bounded wait and GetOverlappedResult(False). IO_INCOMPLETE cannot retire the holder. Actual completed bytes must be0..buffer length and match cumulative channel offsets/cap; copy once, reset event and allocate/reinitialize the next operation only after known terminal completion. ERROR_BROKEN_PIPE as an exact completed/never-issued pipe EOF is distinct from invalid/unknown handle status. Raw output is persisted byte-exact, with no successful truncation. Normal admission requires both channels' actual EOF, no outstanding operation, actual root exit0, Job ActiveProcesses0, no forced termination/cancel, and all parent closes checked.

FR-3 cancellation: sticky failure first requests exact CancelIoEx for each pending operation, records success/ERROR_NOT_FOUND/other error without treating any as retirement, then independently observes actual completion using GetOverlappedResult(False) until the original2s IO retirement deadline/remaining overall deadline. A known terminal ERROR_OPERATION_ABORTED proves a canceled operation completed, but does not make the stage successful. Pending/unknown/unfamiliar outcomes retain server/event/OVERLAPPED/buffer and all other frame holders; no CloseHandle of an unresolved read, no finalizer retry, no overwrite. A request error cannot skip the completion attempt. Real connection operations use the same rule. The job/root natural wait/grace7 and forced2 boundaries do not add time to IO2 or overall2700; forced cleanup remains failure even if kernel group becomes empty.

FR-4 finalization: collect independent primary/typedcancel/native cleanup/after observation errors, preserve exact objects in group when multiple errors exist. Every safe required attempt executes even if a different one fails. When a holder is conclusively releasable, CloseHandle is called once; BOOL failure/exception/uncertain result marks holder UNKNOWN and preserves the raw value/frame until exact parent process exits. Never retry CloseHandle on a numeric handle that may be reused. An event and buffer remain strong while any operation could still reference them. Receipts report natural group and self IO separately; kernel empty does not imply all descendant exit0, nor close UNKNOWN success.

FR-5 native controls run before original NT methods in the same frozen manager/runtime/source context. Immediate and delayed actual ordinary child writers exercise both channels and EOF. A real child descendant retains a write endpoint after root exit so ActiveProcesses/root-only success cannot admit; owned cleanup is observed but denied. Pending cancellation demonstrates request vs completed distinction. A separate disposable ordinary fault child creates a real protected event handle, sets/readbacks PROTECT_FROM_CLOSE, invokes exactly one real close, asserts actual failure/sticky denial/frame retained, emits a bounded diagnostic and exits without clearing/retrying/removing its retained fault. Its parent validates actual process exit/assigned Job empty and parent IO known closed; no Go NT methods are launched on control failure. Ordinary fault test result is a tested negative boundary, not an authorization token or a claim all fault child selfhandles closed before exit.

## 文件结构

One finite adapter source and one ordinary native control source alongside the planned manager. Existing Api and all production methods remain immutable. All new symbols require own fresh graph/impact before edits, source seal, compile/syntax scope truth and independent native startup review. Public source-only backup excludes raw pipe/host/runtime/process data and executables.

## 原 helper 与 stage 上限的准确边界

The parent budget's maximum20 denotes explicitly managed root-stage invocations, not all inherited descendants. The unchanged original restore_source performs native Git show/hash/update calls for73 fixed payloads plus clone/apply/verification; its descendant invocation count exceeds20. Its run_git uses subprocess.run(capture_output=True) without a per-call explicit raw cap. Fixed successful blob/patch bytes are identity/size checked, but this is not a2MiB bound on every inner Git stderr or unchecked failing output. New adapter stdout/stderr caps apply only to the actually managed root stage channels. Descendant helper raw bounding is therefore unresolved for composed startup; preserve the original source and disclose UNKNOWN/STOP rather than imply outer capture bounds inner allocation. If root requires individual helper cap/owned delegate adaptation, add a specific external binding contract, fresh impact and independent controls/review before composing; do not silently modify original function bytes/AST or replace native fetch with an API adapter. No full-manager startup permission follows from this IO subdesign.
