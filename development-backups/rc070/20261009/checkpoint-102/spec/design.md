# Concrete conditional native birth mechanism

## 概述

Local installed subprocess.py excludes its posix_spawn branch when start_new_session=True, which the original owner requests. This is actual source analysis, not a process trace or proof of the fork-exec implementation. Choosing ordinary Popen with a Python preexec_fn to call fexecve reintroduces the pre-collector callback window. The proposed minimal source boundary is three new components; none exists as an approved artifact.

## 对应需求

FR-1 defines raw creation and escrow. FR-2 binds every child instruction before a collector exists. FR-3 defines finite failure semantics and no-launch versus launch-possible branches.

## 技术方案

Component A is a reviewed native parent birth module. Parent preallocates native escrow, actual FD ledger slots and a non-droppable private native registry link before clone3, and validates fixed immutable inputs/private FD plan before child creation, uses a native critical section to block catchable signals in the calling thread, and performs raw clone3(CLONE_PIDFD), flags only CLONE_PIDFD, exit_signal SIGCHLD, no shared-VM/files/sighand/threads/parent/namespace options. The actual returned pidfd/root relationship enters native escrow before any Python result construction, caller signal unblocking, exception check or cancellation propagation. Escrow is the actual creator's private native ownership record, not an authorization field accepted from outside. Once clone3 actually returns an owned pidfd, fixed native stores fill that already-linked record; no allocation, Capsule construction or Python callback is needed to make it reachable. Registry/storage failure is handled before creation; post-creation result/unblock failure leaves the original actual record linked for real cleanup/UNKNOWN, never reconstructing authorization from PID/FD numbers. If Python return/cancel fails, native escrow remains accessible for genuine cleanup/UNKNOWN retention. A Python Capsule/type must expose exactly that actual record and cannot be externally constructed from PID/FD integers. This requires a new native API, not reusing fake Popen internals.

The child continuation is audited native-only machine code, not Python or a libc fork wrapper. It runs on the copied calling thread state but never accesses Python/runtime allocation locks or calls a user handler. A reviewed direct-syscall stub checks/sets subreaper, configures session/private FD map and descriptor inheritance, then execveat(sealed_image_fd, empty_path, fixed_argv, fixed_env, AT_EMPTY_PATH). All error paths only emit bounded genuine exec-error bytes on the owned CLOEXEC status pipe and _exit; they never return to Python. A blocked inherited signal mask prevents user signal-handler execution before the fresh image installs its own reviewed native policy. SIGKILL/SIGSTOP cannot be blocked; early terminal/deadline remains fail-closed, and no child-creation instruction occurs in this stub. Stack protector/profiling/sanitizer/compiler helper calls, PLT linkage, runtime callbacks and unexpected child path instructions must be excluded by actual reviewed machine code/source-build mapping, not by flags alone.

Component B is an owned immutable image sealer. Parent writes bounded reviewed native ELF bytes to its actual memfd with executable/sealing semantics explicitly established on the target kernel. It adds write/grow/shrink/seal restrictions and verifies the actual seals, descriptor identity and complete byte hash before birth. No writable mapping or mutable execution path substitutes for binding; F_SEAL_FUTURE_WRITE alone is insufficient. This proposal has not called memfd/clone3/execveat and headers do not establish availability or permissions. Static ELF begins at an explicitly reviewed native entry; a no-libc/no-CRT build is a candidate but needs complete link-map/disassembly/import/relocation/init-array checks and actual build identity. A static label does not establish no-fork instructions.

Component C is the fixed native root collector from the previous formal proposal. Native birth establishes subreaper before Python/project startup; the root keeps that state through exec and verifies it before BOOTREADY. It has only this private family. It forks nothing before a valid native LAUNCH. BOOTREADY comes from actual source-bound executing root, but is a new protocol event, not the original worker READY/ACK or authority. Parent's original .2 deadline includes all stages. Actual original worker request/G writes still require original readiness/result validators under declared new parent-role semantics.

Before any LAUNCH syscall attempt, source-bound birth stub plus complete root entry/loop prove no descendants have been created. The same actual root terminal and actual owned pipe EOF/drain/close may therefore support aborted-startup-close only, even if nonzero. CLOEXEC status EOF alone is not exec success: early death also closes it. If source/entry is unknown, early terminal is not proof of a sole child. After any LAUNCH attempt, even partial/canceled, collector evidence is mandatory: actual created/adopted pidfd-own-child waitid, genuine reaps and exact private-root P_ALL ECHILD, plus its owned transport EOF/drain/retirement. Proc rows are candidates only. Root must remain alive until EMPTY; child attempts to kill the collector, unowned ancestry, deadline, unexpected protocol or UNKNOWN close never grants empty family. Parent must not kill a process group containing its only collector. Child-private FDs retire via actual child kernel terminal/reap; explicit child close receipts are not invented. Original stderr DEVNULL remains unobservable rather than fake EOF.

## Runtime and trust boundary

Parent native module load and source identity, exact child stub instructions, sealed root image and target Linux kernel semantics are trusted mechanisms that need actual approval. Merely auditing Python _worker AST does not cover them. For abort containment the root may collect Python startup forks without trusting their code, because kernel ancestry/subreaper begins first; this does not authorize child command semantics or prove default-site imports match original worker execution. Worker source/READY/command behavior has its own startup/runtime validation requirement. This architecture grants no publisher credential/issuer/same-client/server-hold/install authority. User-privileged ptrace/code injection and root source replacement are outside this finite model; actual uncertainty must refuse admission.

## Concrete current decision

This is a minimally enumerated mechanism, not presently implementable from existing Python-only helpers. Required native escrow/stub/immutable exec/build/source collector artifacts and target actual controls are absent. No new native family control should be run until a separate finite implementation scope is approved. Direct isolated-loader remains STOP; this native mechanism remains conditional OPEN.
