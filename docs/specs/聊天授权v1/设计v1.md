# 设计文档：聊天授权v1

## 概述
对应需求：FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, NFR-1。

## 技术方案
### 技术选型
Rust既有 ring::hmac/sha2、serde、Mutex/Arc；不新增密码学依赖。Svelte/Tauri IPC负责授权管理；现有JWT HS256发行方产生单所有者sub和jti，验证后生成principal。
### 架构设计
HTTP OAuth验证 → 请求专属 RemoteAuthorization → tools::call_tool 闸门 → ChatGrant检查 → 会话ScopedRuntime → 原有policy/dispatcher → 业务。
MCP的params._meta只在HTTP入口解析；模型arguments中的同名字段不参与认证。所有网络入口设置Remote标记，Actions缺少host conversation则拒绝；本地可信IPC不靠输入布尔切换。

## 数据模型
ChatIdentity包含profile_id、HMAC绑定ID、token_expiry。Grant包含请求ID、绑定、requested/approved scopes、创建/最后有效业务访问时间、expiry/status。全局服务保存分工作区记录而非全局解锁位，测试使用独立服务实例。活跃批准不落盘；应用重启后重新审批。任务档案依旧使用现有加密存储，但加入稳定会话命名空间。

## API 设计
- MCP auth_status()：仅当前调用身份的状态及下一步。
- MCP request_chat_authorization(scopes)：只创建/读取自己的pending请求，不能批准。
- Tauri manage_chat_authorization(profile_id, action, request_id, scopes, exclusive)：local UI审批/拒绝/撤销/列表，所有动作显式白名单。
- call_tool：最外层授权优先于任何workspace或harness访问；递归后台执行仍需检查。

## 文件结构
新增auth聊天授权模型/存储/闸门/OAuth身份及测试模块；新增tools聊天运行域；新增commands聊天审批和src/lib的API及面板；修改mcp/listener、mcp/server、tools/context、dispatch、auth/oauth_flow、auth/mod、commands/mod、lib、工作区页面。每个新增Rust/Svelte文件控制500行以下；既有大文件只增加薄接入，新增复杂逻辑抽出。

## 设计决策
### 决策 1: 元数据关联不是认证（关联需求: FR-1, FR-5）
openai/session是官方关联字段，不是签名身份证明。仅用于与服务器已验证OAuth身份组合的普通ChatGPT防串话；严格公网部署须验证OpenAI客户端mTLS/可信入口。不能把任意客户端自行填的ID宣传为密码学证明。
### 决策 2: 重启不持久恢复许可（关联需求: FR-2）
选择fail-closed而非自动恢复Grant。加密任务档案可在同一会话重新批准后访问，但重启不自动重跑任务。
### 决策 3: 运行域与文件权限分开（关联需求: FR-3, FR-4）
任务API、进程API、history/harness域隔离；授权文件工具仍能查看批准的共享工作区。恶意exec工作负载需要另行OS隔离，当前不作这一承诺。
### 决策 4: 旧Actions fail-closed（关联需求: FR-1, FR-5）
不把Actions请求body或HTTP自报header当成可信ChatGPT会话。保留协议/本地任务控制，但未建立可信会话通道前业务拒绝。

## 测试策略
纯状态机：A/B、账户/工作区、scope、pending去重/过期、idle/absolute、撤销、独占、并发、容量、敏感输出。集成：真实统一入口及HTTP，模型伪造arguments、危险模式旁路、异步后台再次授权、task/session/cwd/history/harness隔离。OAuth：JWT错误、过期/nbf、resource、PKCE、callback、code重放。原有本地核心测试保留，网络行为安全变化明确更新预期。公网/原生UI单列手动验收。

## 风险评估
统一入口为HIGH（图谱23个直接调用）。风险缓解：不另建执行内核、授权前无业务副作用、先负向用例、独立候选分支。容器无Rust编译器且无联网：本地可做静态/Node检查，Rust应由CI真实执行，未成功不能报通过。
