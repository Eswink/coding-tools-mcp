## Model and API

rc_publication_types.py defines frozen, deeply immutable, bounded new records, using tuples and exact enum/type checks. SourceIdentity/codecs are imported unchanged. Public entrypoints revalidate the complete supplied record through the unchanged strict codecs, including nested records, rather than relying only on nominal frozen-dataclass types. New records do not serialize mutable dicts or freeform diagnostics, secrets, paths, commands or URLs. Existing 256 KiB JSON, 16 nesting levels and bounded collection/string rules remain. New bounds: six expected assets; up to 16 observed assets to preserve and reject extras rather than truncate; up to 32 journal entries; positive IDs below 2^63. Fixed-code errors never echo raw inputs.

- AssetSpec: name, family, media_type, size, sha256. Validate each of the four payload records through unchanged PayloadObservation (including its2GiB bound), then compare names with unchanged payload_names(version). Evidence bounds are separate: provenance1..256KiB, checksums1..8192bytes. MIME contract is fixed here with test-only parity against current consumer constants, avoiding runtime import of consumer/network modules
- PublicationRecipe: SourceIdentity, exact tag v<version>, six AssetSpec records, prospective notes SHA256, consumer-plan SHA256, policy/schema revision, non-authority fields. Require canonical tuple order nsis/deb/appimage/cloud/provenance/checksums. Fingerprint = SHA256 of fixed domain bytes 'rc-publication-contract/v1:recipe\n' followed by unchanged encode() of the deeply revalidated recipe. It is computed, not a supplied authority field. Alternate asset ordering is rejected rather than assigned another identity
- ReleaseObservation: expected SourceIdentity, numeric release ID, reported tag, reported_target_commitish (exact SHA string or None), draft/prerelease observations, notes digest and bounded asset rows. A reported matching target_commitish is a caller claim, not resolution/authentication of a Git tag. Missing target remains unknown; different target conflicts. It never clears existing-tag or no-create prerequisites
- AssetObservation: asset ID/name/state, reported media_type, size, sha256. Missing media/digest/size may be None to represent incomplete evidence; known sizes permit0 only so a starter/empty observation can be retained and rejected by classification, with maximum2GiB. Known digests have exact lowercase SHA256 grammar. Missing MIME is incomplete; wrong MIME, zero size, non-uploaded state or differing digest is blocked/conflicting. Never count an unobservable property as matched
- AttemptObservation: exactly one immutable record for each logical attempt, operation kind (create_draft/upload_asset/publish), fixed target release ID (None only for create), optional exact asset name, outcome (prepared_only/response_success/response_failure/outcome_unknown), and typed non-secret response identity. Record requested_draft/requested_prerelease/requested_make_latest for create and publish: create must be true/true/'false', publish false/true/'false'. These are untrusted intention observations, not executable request objects or returned release facts. Upload requires those fields absent. A success response's release or asset identity must match the exact operation, expected recipe and target. No HTTP method/path/payload is emitted
- InventoryCheckpoint: expected SourceIdentity/tag and optional expected_release_id; visibility enum(reported_visible/denied/unknown); completeness enum(complete/incomplete/unknown); lookup enum(found/absent/inaccessible/unknown); tuple of at most2 matching ReleaseObservation records. More than one match is collision; over-limit input fails rather than truncates. Absence classification requires lookup=absent, completeness=complete, visibility=reported_visible and zero records. None/empty alone never means absence. Found requires one or two records; inaccessible/unknown remains unknown. Each release binds the same source/recipe/tag; when a release ID has been established, continuation checkpoints must bind it. These are assertions, not real-time freshness, draft visibility, ownership or absence proof
- JournalEntry: contiguous sequence index, kind (attempt/checkpoint), and exactly one Optional[AttemptObservation] or Optional[InventoryCheckpoint] field populated. The unchanged codec supports this wrapper; do not introduce a general tagged union or alter its decoder
- JournalObservation: recipe fingerprint, tuple of at most32 ordered JournalEntry records, source identity, transaction identity digest. Transaction markers and claimed owner matching do not authenticate ownership
- ReconciliationReport: classification, fixed reasons, observed identifiers; every non-authority flag fixed. No next_action, request object, ready/eligible state, authority token or execution capability

rc_publication_contract.py provides validate_recipe and classify_inventory only. Exact allowlist: MCP_<version>_x64-setup.exe; MCP_<version>_amd64.deb; MCP_<version>_amd64.AppImage; cloud-linux-amd64.tar.gz; RC_PROVENANCE.json; SHA256SUMS_<version>.txt. Require exact families/MIME/names, no duplicate or normalized aliases, positive bounded sizes and lowercase SHA256. validate_recipe accepts caller-supplied checksum bytes (<=8192), checks exact sorted five-file coverage excluding the checksum file, strict ASCII/lowercase digest/two-space/newline grammar, and checks checksum bytes' own size/hash against its sixth AssetSpec. This is consistency, never payload-byte or provenance authenticity verification. A missing or unverified consumer-plan reference stays a blocker even if all checksums match. Do not reimplement the consumer evidence schema.

Inventory classifications: absent_reported, draft_empty_reported, draft_partial_reported, draft_complete_reported, published_complete_reported, collision, unknown. Each is an observation, not permission. Only complete known visibility can yield an absence report, still unverified. Reject/flag extra/duplicate asset names or IDs, renamed assets, wrong sizes/digests, starter/empty state, conflicting tag/source/prerelease/notes, and a published partial inventory. A marker/recipe match may be classified as matching_claim but never owned/authenticated. Existing identical published observations permit only a read-only classification; no republish proposal.

rc_publication_reconcile.py validates journals and compares later observations. A journal starts with an explicit checkpoint: absent, matching draft, matching published, or unknown. Only a reported absent checkpoint can precede create; a matching initial draft supplies only the explicitly listed pre-existing asset identities and a claimed target. A successful create establishes the journal's sole release ID from its typed response. All later uploads/publish bind that same ID. A fresh matching draft checkpoint is required after each successful operation and before another operation; sequence order is merely reported ordering, not authentication. Every continuation checkpoint must preserve every already-accounted asset ID/name/size/hash/MIME and may not add unexplained assets. Extra remote assets or disappearance/replacement are conflicts, not a way to make an incomplete journal complete. This continuation rule is distinct from later reconciliation checkpoints after a stop: those may report new IDs/state, but cannot add them to the accounted-success inventory or enable another attempt.

Valid synthetic shape: initial checkpoint, draft-create success when absent, matching draft checkpoint, zero-to-six unique successful upload attempts each followed by a matching checkpoint, then publish only after all six unique upload IDs or explicit initial-draft asset IDs are accounted for by the complete checkpoint. Pre-existing inventory remains an unverified ownership claim; it cannot authorize writes. Track attempted asset names separately from successful names and forbid retry even after a definite failure. A prepared_only attempt is not proof a request was or was not sent. No upload before a matching draft checkpoint; no publish before exact completeness; no operation after a matching published checkpoint or publish success; no delete/overwrite/rename/tag operations at all.

prepared_only or outcome_unknown creates a monotonic uncertainty latch: later checkpoints may describe a matching or conflicting state, but cannot erase uncertainty or permit any subsequent attempt. response_failure also terminates subsequent attempts conservatively; it never proves absence of a side effect. After unknown create/upload, retain a later checkpoint reporting an otherwise unseen release/asset ID as unverified reconciliation evidence; do not discard it, count it as a successful response, or establish ownership. Later inventories cannot substitute an observed asset for a failed/unknown upload. A new journal/run attempt/transaction digest is not a replay escape hatch; this phase cannot validate global cross-run uniqueness and every report carries that fixed limitation. Reconciliation result always requires external authenticated review/admission, never next mutation. Publication observation and uncertainty/failure are independent monotonic facts: a later inaccessible/failed read does not erase already reported publication, and a matching read does not clear uncertainty. Observed publish success remains published_unverified; no public-download record or verified-publication factory is in this phase, and lack of public proof never suggests remote rollback.
